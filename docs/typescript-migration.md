# TypeScript migration study

Research date: 2026-08-26. Scope: whether/how to migrate this plugin to TypeScript, and whether `scaleway-sdk-js` (https://github.com/scaleway/scaleway-sdk-js) can replace the hand-rolled `shared/api/*` axios client layer as part of that. This is a Step-1 research/plan document per the `feature-loop` workflow — **no code has been changed**. Every claim below was checked directly (repo files read, `scaleway-sdk-js` inspected via its GitHub API/npm registry) unless explicitly marked "unverified" / "via web search, not independently confirmed."

## TL;DR

- **`scaleway-sdk-js`'s API coverage is genuinely good news**: dedicated, actively-maintained packages exist for every Scaleway product this plugin talks to (Functions, Containers, Registry, Account/Projects, Domains, Crons, Triggers, Tokens) — see the coverage table below. The "swap the API layer" half of this idea is viable on paper.
- **But the SDK is ESM-only** (`"type": "module"`, no CommonJS export condition, confirmed on both `@scaleway/sdk-function` and the umbrella `@scaleway/sdk`). This plugin is currently plain CommonJS with no `"type"` field. Using the SDK forces a real decision: convert the whole plugin to ESM, or reach for it only via dynamic `import()` from CJS. This is a bigger, separate decision from "adopt TypeScript."
- **TypeScript adoption itself is decoupled from the SDK question.** `tsc` can emit CommonJS just fine — you can convert this codebase to TypeScript while keeping the existing axios-based `shared/api/*` layer entirely as-is, with zero ESM/build-step forcing function beyond "add a `tsc` step."
- **Migration surface is moderate, not huge**: 42 source `.js` files / ~3,437 LOC (excluding `tests/`, `examples/`, `node_modules/`); the test suite is actually larger now — 46 files / ~6,802 LOC — largely from this session's own coverage work.
- **The test-suite blockers found for the earlier Bun investigation (`docs/fixing-plan.md` M7) do not apply here.** `rewire` and `@jest/globals` both depend on real Node CommonJS module internals; `ts-jest`/`babel-jest` still run on real Node, so neither breaks the way they did under Bun's own module loader/test runner. This makes a TS test-suite migration meaningfully lower-risk than the Bun one.
- **No build step exists today** — `CLAUDE.md` states this as a deliberate choice ("Plain CommonJS ..., no TypeScript, no build step — `main` in `package.json` points straight at `index.js`"). Any TS adoption changes that, at minimum to a `tsc` compile step; this is the main real cost, independent of the SDK question.

## 1. `scaleway-sdk-js` findings

**Package**: published on npm as `@scaleway/sdk` (umbrella package, currently `4.0.5`) which depends on ~50 per-product packages (`@scaleway/sdk-function`, `@scaleway/sdk-container`, `@scaleway/sdk-registry`, `@scaleway/sdk-account`, `@scaleway/sdk-domain`, `@scaleway/sdk-iam`, etc.) — the products can also be installed individually. Source: `packages_generated/<product>/package.json` per product, a pnpm-workspace monorepo (`packages/` for the hand-written core: `client`, `configuration-loader`, `sdk-react[-hooks]`; `packages_generated/` for the ~50 auto-generated per-product API clients).

**Maintenance**: both `@scaleway/sdk` (`4.0.5`) and `@scaleway/sdk-function` (`2.11.0`) show a last-publish timestamp of `2026-08-26` (today, per the npm registry `time` field) — actively, frequently published. Licensed Apache-2.0.

**Module format — the critical finding**: every package checked (`@scaleway/sdk`, `@scaleway/sdk-function`, `@scaleway/sdk-client`) has `"type": "module"` in `package.json`, with `exports` only providing a `"default"`/`"types"` condition (no `"require"` condition, no `main` field). This is **ESM-only** — there is no published CommonJS build. Confirmed directly from the packages' `package.json` on npm/raw GitHub, not inferred from the README.

**Node/engines**: `"engines": { "node": ">=20.20.2" }` on the packages checked — slightly stricter than this repo's current `"engines": { "node": ">=20" }` (set this session per M4); would need a small bump if adopted.

**Written in TypeScript**: yes, source is `.ts` throughout (`api.gen.ts`, `types.gen.ts`, `marshalling.gen.ts` per product), with generated `.d.ts` output — this is the actual draw for "migrate to TS + use this SDK" as a combined idea, since the types would come largely for free per-endpoint rather than needing to be hand-written against this plugin's own axios calls.

**Pagination/auth model**: the SDK has built-in pagination helpers (`enrichForPagination`, `.all()` / async iteration per the README) — this would directly obsolete finding #4 in `docs/fixing-plan.md` (missing pagination in `listNamespaces`/`listFunctions`/`listContainers`) if adopted, rather than needing the hand-rolled pagination loop that finding's fix proposes. Auth/region/project scoping is handled by the shared `@scaleway/sdk-client` core package (not deeply inspected beyond confirming it exists and is also ESM-only).

## 2. What a TypeScript migration of this codebase specifically requires

### Current state (verified by reading the repo directly)

- `package.json`: `"main": "index.js"`, no `"type"` field (defaults to CommonJS), `"engines": { "node": ">=20" }`, no build script.
- No TypeScript anywhere in the plugin's own source. The only `.ts`/`tsconfig.json` in the repo is `examples/typescript/` — a fixture _example project_ showing end users how to write a TS function handler, compiled by their own tooling; unrelated to the plugin's internals.
- `eslint.config.mjs` is a flat config using `js/recommended` only — no `typescript-eslint` today.
- Jest config lives inline in `package.json` (`"jest": {...}`), transform-free (plain `.js`, no Babel/ts-jest step).
- `bluebird` was fully removed this session (17 files migrated to native async/await, see `git log` `refactor(*): migrate off bluebird` commits) — the whole codebase is already async/await-based, which is a smaller conceptual jump to typed async code than the Promise-chain style it used to be.

### The build-step question

Since `main` currently points straight at CommonJS `index.js` with no compile step, adopting TypeScript means introducing one, at minimum `tsc` compiling `.ts` → `dist/*.js`. Two materially different versions of this, depending on the SDK decision:

- **TS-only (keep axios-based `shared/api/*`)**: `tsconfig.json` with `"module": "commonjs"`, `"target": "es2022"` (matches the `node >=20` engine), `"outDir": "dist"`. `package.json` `"main"` moves to `"dist/index.js"`, `"files"` includes `dist/**`, source `.ts` is not published. This is a self-contained, low-blast-radius change — the published package still loads as CJS exactly as it does today, nothing about how Serverless Framework loads this plugin changes.
- **TS + SDK swap**: forces the ESM question (see decision points below) because the SDK has no CJS build. Either the whole plugin becomes `"type": "module"` (bigger, touches how Serverless Framework loads it, how Jest runs it, how `require`-based internals like `shared/api/endpoint.js`'s dispatch work) or the SDK is reached via scoped `await import(...)` inside otherwise-CJS async functions (workable — Node supports dynamic `import()` from CJS — but adds friction and inconsistency, since the rest of the codebase's `require()`s stay synchronous).

### Migration strategy options

1. **Big-bang**: convert all 42 files to `.ts` in one pass, add `tsconfig.json` + `typescript-eslint`, ship compiled `dist/`. Fastest to a "real" typed codebase; highest single-PR diff risk, and blocks on resolving the build-step/ESM question before writing a single file.
2. **`allowJs`/`checkJs` + JSDoc first**: add a `tsconfig.json` with `"allowJs": true, "checkJs": true, "noEmit": true`, annotate existing `.js` files with JSDoc `@param`/`@returns` types, get real type-checking (`tsc --noEmit` as a new `npm run typecheck` script, wired into CI) with **zero change to what ships** — no `dist/`, no `main` change, no build step yet. Converting individual files to real `.ts` becomes a later, optional, file-by-file decision. Lowest risk, defers the hard build-step/ESM decision indefinitely if desired.
3. **Incremental `.ts`/`.js` coexistence**: `"allowJs": true` (without `checkJs`), convert files to real `.ts` one at a time, both extensions coexist during the transition (mirrors this session's own file-by-file Bluebird-removal pattern, which worked well as an execution model). Moderate risk, moderate payoff — but unlike option 2, this does require committing to the build-step/`main` change on day one, since the moment one `.ts` file exists, publishing needs compiled output.

### Test suite impact

- `ts-jest` (or `babel-jest` + `@babel/preset-typescript`) as the Jest transform is the standard approach and would need adding as a dev dependency.
- **Unlike the Bun investigation**: `tests/deploy/buildAndPushContainers.test.js`'s `rewire(path).__get__(...)` usage and every test file's explicit `@jest/globals` import both continue to work under `ts-jest`, because it still runs on real Node with real CommonJS module internals (the Bun blockers documented in `docs/fixing-plan.md` M7 were specifically about Bun's _own_ module loader/test runner lacking `Module.prototype.load` and rejecting `@jest/globals` imports outright — neither applies to `ts-jest` running under Node).
- Tests do not need to convert to `.ts` at all for this to work — Jest/`ts-jest` can type-check and run `.ts` source files while `tests/**/*.test.js` stays plain JS indefinitely, since Jest doesn't require both sides of a test to share a language. Given tests are now the larger mass of code in this repo (6,802 vs. 3,437 LOC), leaving them as `.js` is a reasonable way to bound the migration's scope.

## 3. Open decision points (not resolved here — genuinely the user's call)

1. **Decouple TS-adoption from the SDK swap, or do both together?** Recommend decoupling: TypeScript-only (keeping the current axios `shared/api/*` layer) is a self-contained, CJS-preserving change with a well-understood build step. The SDK swap is a separate, larger decision gated on the ESM question below — bundling them means the TS migration inherits the SDK swap's risk even if only the typing benefit was wanted.
2. **If the SDK swap happens: full ESM conversion of the whole plugin, or scoped dynamic `import()` from CJS?** Web search indicates Serverless Framework v3 (3.2.0+) supports ESM plugins (`"type": "module"` in `package.json`, `peerDependencies: { serverless: "^3.2.0" }`) — **this was not independently verified against the `oss-serverless/serverless` source in this session** and should be confirmed directly (read its plugin-loading code, or a working ESM-plugin example) before committing to this path, given how central it is to the decision.
3. **Migration strategy** (big-bang vs. `checkJs`-first vs. incremental `.ts`/`.js` coexistence, section 2 above) — a judgment call on effort/risk tolerance, not something to silently pick. Given this repo just finished a large modernization pass this session (M1-M6 in `docs/fixing-plan.md`, all now merged), the lower-risk `checkJs`-first option is a reasonable default recommendation, but it's the user's timeline/appetite to weigh.
4. **Sequencing against already-tracked modernization work.** `docs/fixing-plan.md` M7 (Bun adoption for dev tooling) and M8 (test-parallelization hardening) are both still open/optional. A TS migration that also touches the Jest config would collide with M7 if both were attempted around the same time — worth deciding which comes first, or whether M7 is dropped in favor of this instead (a TS+Jest combination and a TS+Bun combination are different enough that doing both is likely wasted effort).
5. **Whether to ever convert the test suite itself to `.ts`.** Not required for any of the above (see previous section) — worth deciding explicitly rather than letting it happen by default file-by-file drift.

## 4. Suggested phased plan — proposal only, pending confirmation

**Phase 1 (low-risk, reversible, no build step, no `package.json` shape change):**
Add `typescript` and `typescript-eslint` as dev dependencies, a `tsconfig.json` with `allowJs: true, checkJs: true, noEmit: true` targeting the existing `.js` tree, and a `npm run typecheck` script. Annotate a handful of files with JSDoc types to prove the setup catches real issues (a good candidate: `shared/api/utils.js`, given it's small, central, and was just touched for the `CustomError` fix). Nothing about what's published changes.

**Phase 2 (only if Phase 1 proves valuable — proves the CJS build pipeline end-to-end on one low-risk file):**
Pick one small leaf module (e.g. `shared/constants.js`) and convert it to a real `.ts` file. Wire up the minimal `tsc` build (`outDir: dist`, `module: commonjs`), change `package.json` `main`/`files` to point at `dist/`, and verify via `npm link`/a local `serverless deploy` against a test service that the plugin still loads and runs identically under the Serverless CLI. This is the phase that actually derisks "does our build step work," before scaling to the rest of the tree.

**Phase 3:** Convert remaining files incrementally, module by module, each independently tested and committed — same execution shape as this session's file-by-file Bluebird removal.

**Phase 4 (separate track, only if the SDK swap is wanted):** Spike the ESM question directly against `oss-serverless/serverless`'s actual plugin-loading source (resolving open decision #2 above), then prototype one real API call end-to-end (e.g. `@scaleway/sdk-account`'s `createProject`, since it's small and already has a live test harness in `tests/utils/misc/index.js`) before rippling the swap through the rest of `shared/api/*`.

## 5. Post-migration: independent review findings (2026-08-26)

The migration executed (all 42 non-deferred files, in one continuous session, not the phased/optional rollout proposed in section 4 above — the user confirmed "TypeScript only" and "incremental per-file conversion" as the scope, and it proceeded file-by-file with a full verify loop per batch) was checked afterward by an independent, adversarial review pass: every non-null assertion, cast, and "behavior preserved" claim re-verified against the pre-conversion `.js` source via git history, not trusted because the same session wrote both.

**Result: two real, low-severity behavior changes, both undisclosed in their commit messages, both strictly safer than the original (no crash risk introduced, no regressions) — not the zero-deviation result the commit messages implied.**

1. **`deploy/lib/createFunctions.ts` (`validateRuntime`'s EOL/EOS log messages) — an actual latent bug fix, not disclosed as one.** The pre-migration `.js` printed `` `Runtime ${runtime.name} is in End Of Life...` ``, but `runtime` here is looked up from a map that only ever stores `{status, statusMessage}` — never `.name` — in both the original and converted code. So this line always printed "Runtime undefined is in End Of Life..." before the migration. Once `existingRuntimesByName` got a real TypeScript type, `runtime.name` became a compile error, which is almost certainly why it got changed to `currentRuntime` (the real runtime string) during conversion. Genuinely correct fix, real user-facing improvement (the warning now names the actual runtime) — but commit `e6478a8` documented two _different_, deliberate fixes for this file and didn't mention this one.
2. **`shared/api/utils.ts` (`manageError`'s `invalid_arguments` detail loop) — a narrowed edge case, not disclosed.** Changed `for (const details of err.response.data.details)` to `for (const details of err.response.data.details ?? [])`. If the API ever returns `type: "invalid_arguments"` with no `details` array (a malformed/inconsistent response shape), the original threw `TypeError: ... is not iterable`; the converted version now silently skips the per-argument detail lines instead and returns a bare message. Safer direction, narrow trigger condition, but a real, silent divergence from the "zero behavior change except two documented fixes" claim made throughout the migration's commits.

Nothing else the review checked turned up a problem: every `!` assertion matched an assumption the original untyped code already made unguarded; the `export =` conversions produce identical `module.exports` shapes (including preserved non-enumerability on the `rewire`-replacement helper exports); the two officially-documented fixes (`shared/domains.ts`, `deploy/lib/deployTriggers.ts`) check out exactly as described.

Not corrected retroactively by amending the original (already-merged) commits — recorded here instead, since rewriting merged history isn't worth it for two safe, low-severity deviations. If either behavior is ever reverted or changed further, whoever touches those two spots next should know they're intentional-in-effect (if not intentional-in-origin) improvements, not accidents to "fix back."

## 6. Follow-up: `shared/api/index.ts` converted (2026-08-26)

Originally deferred alongside `shared/api/endpoint.js` as "the mixin-class-construction boundary" (section 4's open questions). Converted as a small, well-scoped extension while typing `tests/utils/*` test helpers (a separate, narrower task): those helpers construct `AccountApi`/`FunctionApi`/`ContainerApi`/`RegistryApi` directly via `new X(url, token)`, and with `shared/api/index.js` still untyped JS, TypeScript inferred an incorrectly _narrow_ type for these classes (just `{apiManager}`, since it can't see through a dynamic `Object.assign` call) rather than falling back to `any` — actively wrong, not just imprecise, and it would have blocked real type-checking on any new `.ts` consumer of `shared/api`, not just these test helpers.

Solved with TypeScript's class/interface declaration-merging idiom: each class declares only `apiManager` in its body (what the constructor actually assigns directly), then a same-named `interface X extends <mixin module types>` adds the rest of the Object.assign-built surface to the class's static type — asserted, not verified, the same way the definite-assignment-assertion pattern used everywhere else in this migration documents a runtime guarantee TypeScript can't check on its own. `@typescript-eslint/no-unsafe-declaration-merging`, `no-require-imports` (needed for `import x = require(...)`, the only correct TS syntax for importing an `export =` module), and `no-empty-object-type` are disabled specifically for this one file in `eslint.config.mjs`, not repo-wide.

**`shared/api/endpoint.js` remains deferred** — its `getApi(object)` dispatcher is called with many structurally-different `this` types across the different top-level plugin classes (`ScalewayDeploy`, `ScalewayInvoke`, etc., each of which declares its own narrower context shape), which needs a real generic/union design, not the same mechanical pattern. Still a separate decision.
